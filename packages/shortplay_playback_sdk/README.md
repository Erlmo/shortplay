# ShortPlay 本地播放调度 SDK

Dart 调度与下载模块，加 Android / Apple 原生媒体 IO 适配。无 TTVideoEngine 二进制、AppID 或 License 依赖，不承担视频解析接口、解密算法或编解码实现。

## 组成

- `PlaybackSession`：当前播放状态驱动的单队列、取消、去重、失败上限和跨集任务生命周期。
- `PlaybackBufferMonitor` / `PlaybackBufferGate`：独立300ms采样、缓冲安全滞回、卡顿后队列恢复，采样不调用play/seek或重建。
- `prepareFirstFrame`：静音并在暂停状态准备，等待真实首帧后停放；由宿主负责失败和取消时释放实例。
- `PreparedPlaybackStore`：按视频、清晰度、源世代和本地路径管理已就绪实例，取出即交接所有权，取消旧准备不会销毁已交给前台的实例。
- `PlaybackCommandQueue`：同一实例的停放/激活事务串行，防止快速来回切集时旧命令覆盖新播放状态。
- `PlaybackResourceCache`：有容量上限的 LRU 元数据缓存、并发请求合并、过期检测和失效写入隔离。
- `MediaDownloader`：直连 CDN，Range 下载、按实际已读偏移续传、在途请求复用和真实 HTTP 取消。
- `MediaCacheStore`：原始媒体字节缓存，预加载、播放与下载共用；不缓存解密后的数据或密钥。

集成在 `PlayerPreloadMixin`、`TheaterVideoPreloadManager` 和现有播放页。页面/控件和原生解码器不替换。Android 和 Apple AVPlayer 通过原有事件通道补充 `bufferedAhead`（毫秒），不更改通道名。Apple 自定义 BVC2 后端尚无可比较的缓冲时长，保持宿主原先“播放进度前进3秒且不卡顿”的兜底；不会把已解码的10帧冒充14秒网络缓冲。

## 有代码依据的调度规则

观察对象为官方 Android SDK `1.52.1.13`，不代表红果线上动态配置：

| 策略 | 原 SDK 观察 | 本地 SDK 接法 |
| --- | --- | --- |
| 数据预取 | 当前缓存严格超过14秒启动；严格低于5秒停止 | 同样的滞回阈值，卡顿、暂停、后台和离页取消后台准备 |
| 任务顺序 | 未来3条、FIFO串行 | 下一集先准备首帧，其后两集预热文件头；下一季任务排在后面 |
| 重试 | 成功去重，失败累计上限3，取消不算失败 | 后续状态更新才重试，不在失败回调中忙循环 |
| 预渲染 | 默认只N+1，已准备实例交给正式播放 | 维持原有前/当前/后播放器窗口，优先复用下一集实例 |
| 地址标识 | 正式播放与预加载必须保持源身份一致 | 同一解析结果与完整URL复用，不删query猜测缓存key |
| 缓存完成 | 当前缓存完全就绪时也可触发 | 本地已缓存当前集视为完全缓冲；本地下一集无需等待网络阈值 |

原 SDK 默认每条预加载800KB，可被动态配置覆盖。本 SDK 现在先预取800KiB原始媒体字节，再调用宿主既有解密头部准备及首帧流程。下载默认并发1、读超时5秒来自观察配置；最多3次续读是本项目的有界重试策略。

TT预渲染调用 `prepare()`、禁用自动播放并配置范围读取。宿主现在也不依赖play推进进度：Android复用已prepare且绑定Surface的暂停实例；Apple AVPlayer在rate0时preroll，已有BVC2后端使用原有暂停时钟解码。均等待真实首帧事件，不把创建或preroll完成当首帧。

V2代码中当前renderStart、预载成功和缓存安全分别可唤醒预渲染。已预载成功的N+1在当前集出画后可开始，不重复等14秒；尚未预载的网络任务仍受原缓冲保护。该V2是可选策略版本，不声称官方所有配置都启用V2。TT的isPrepared并不等于首帧已出，本项目保留真实首帧作为更严格的交接门槛。

## 边界与容量

- 地址/密钥/画质/预热标记在同一缓存条目内，宿主容量16个条目（本项目选择）。按过期时间提前30秒失效。
- 换清晰度或清理列表后，旧异步结果仍可返回其原调用者，但不会写入新缓存。
- SDK的取消不撤销已开始且没有原生取消句柄的C预热操作。该调用结束后才放行下个预热任务；已取消任务不会发布播放器或启动后续队列。
- 未加密HTTP和加密媒体均复用原始字节缓存；Android替换DataSource IO，Apple通过资源加载器复用已预取对象，解码器不替换。
- Apple普通HTTP冷播在没有有效缓存元数据时仍走原生URLAsset；不支持Range的200前缀不会发布到共享缓存，完整下载可回退顺序GET。
- SDK仅维护独立的媒体缓存目录，不清理用户已经下载的离线视频。
- 此 SDK 不包含解码器优化、ABR、TT网络传输算法，也不保证不同网络和设备的首帧时延。

## 使用

```dart
final session = PlaybackSession(
  run: (index, work, cancellation) async {
    // 调用宿主的首帧准备或文件头预热，过程检查 cancellation。
    return true;
  },
);
session.start([
  const PlaybackSource('episode-1'),
  const PlaybackSource('episode-2'),
], 0);
session.update(
  firstFrame: true,
  active: true,
  buffering: false,
  played: Duration.zero,
  bufferedAhead: const Duration(seconds: 15),
);
// 切集后start新会话；离页close。
session.close();
```

## 下载与媒体缓存

三端共享完整URL的SHA256身份、总长度、过期时间、ETag以及校验后的原始数据块。只有完整块或已知文件末尾的短块可以发布，缓存缺口与损坏均回到网络，不伪造EOF。HTTP206严格核对范围和长度，断流从实际收到的位置续读；取消实际终止请求，已完成的块仍可保留。

媒体预算300MiB，默认有效期1小时，有已知有效期时沿用。按访问时间淘汰、32KiB块、SHA256校验、原子发布和完整URL身份均为本项目的实现选择；原SDK观察到的默认容量也是300MiB，但默认年龄是14天。32KiB在原代码中只证实为读取缓冲大小，没有证明其磁盘块大小。

已确认原下载器的Range、identity、偏移推进与取消，以及缓存总量/连续前缀的区分。原生MDL的内部洞合并、磁盘布局与淘汰算法未取得可靠函数体证据，本模块不声称完整复刻。跨语言缓存和本机HTTP测试覆盖了续传、取消、损坏、过期与读取复用。

## 首帧与切集复用边界

仅下一集新建预渲染实例，上一集保留是本项目已有三播放器窗口的适配。取出实例后从后台store移除，播放中实例不受后台清理影响。只有同源、就绪且无错误的实例可复用；换画质、替换源、跳集、失败或取消不得发布过期实例。完成的上一集重新播放前先定位，再恢复速率、音量和播放。

当前支持准备/出画/交接/取消/释放状态，并没有迁移TT的native codec pool或自动预解码暂停算法。Android保持Surface和Texture，Apple保持原有像素输出；页面和解码器不替换。新逻辑通过自动化回归和三端构建，Apple新增preroll实际首帧效果仍需真机确认，不宣称完成官方引擎性能对齐。

## 缓冲调度与卡顿恢复

REA的V1/V2都证实300ms缓冲采样、严格>14秒启动预取/<5秒取消、尾端position+buffer+1000ms达到总长即视为完整。V2区分磁盘完整/播放器缓存完整，磁盘完整要求所有资源的连续前缀覆盖各自总长。当前宿主已下载文件沿用原有校验；800KiB预取完成不能冒充整集缓存完整。

新增原生getBufferState只查询，不控制播放。当前引擎的轮询由用户播放意图而非isPlaying驱动，卡顿时播放进度不动也继续检查；页面隐藏、用户暂停、拖动期间、完成、失败、切集和退出会停掉轮询/后台任务。迟到快照在seek、pause、新遥测或释放后不会覆盖新状态。同一轮询不并发重入。暂停/后台停轮询属于宿主生命周期适配，不能冒称TT Java策略统一如此。

TT取音频/视频队列的最小缓冲，本宿主保留后端可提供的公共可播放时长：Android totalBufferedDuration、Apple当前位置连续loadedTimeRanges。Apple BVC2仍为未知，不把帧数转换成假缓冲秒数；未知后端保留本项目3秒实际进度兜底，卡顿/暂停后需重新积累，等待墙钟时间不算恢复。

普通bufferStart/bufferEnd与致命错误分开处理，卡顿结束不执行强制play、seek、重建或重新解析；现有原生内核自然恢复。后台预取恢复仍需重新满足安全缓冲或完整缓存条件，单纯bufferEnd不放行。V2对网络卡顿的reason/首帧筛选不能直接映射到只暴露布尔buffering的现有后端，本宿主更保守地暂停所有缓冲期间的后台工作。

引擎receivedError与retry的模型重取/备用URL/codec降级是不同路径；当前没有足够候选URL身份信息，不移植猜测的切CDN或定时重建。原生再缓冲播放阈值和帧饥饿算法尚未查明，本模块是已验证Java调度规则的宿主适配，不是完整内核复刻。

## 网络重试与CDN候选

REA证实候选来自同一VideoInfo的main/backup字段，按顺序交给下载器；不是同720p的所有URL混在一起。宿主只注册同一条媒体的最多4个有效HTTP(S) URL，不改画质、编码或密钥，不生成域名。预热、媒体预取、离线下载与正式读取都先注册同一组候选。

显式候选遇HTTP400..599会在当前操作禁用并尝试下一条；单URL403不会无限重试。连接失败、超时、断流可有限续读；用户取消、TLS证书、非法Range/压缩响应、内容身份变化均终止。模型解析只对明确可重试的瞬时错误重试，解密/参数/无效结果不会盲目重复。普通卡顿不触发错误重建。

三端仍按完整物理URL缓存。已有字节时切候选必须校验总长及32KiB前缀摘要或可信强ETag；不符合就拒绝，不能仅凭长度拼片。无锚点时只能同源续读；尚未交付字节的冷失败可以先切备选再建立身份。Dart切候选时重新获取尚未交付的有界Range以避免混入失败请求的半段，原生流则按已交付offset续读。

预算是宿主适配：原生每次IO失败链max(3,候选数)，有效短206进度不耗失败预算，锚点校验每候选额外至多一次且受同取消范围约束。Dart显式候选遍历一圈，单URL最多3次；其100/200ms退避是本项目选择。原SDK引擎连续错误计数和MDL候选循环是不同层，未证明native全局预算。现有引擎上层仍可能重开IO，不能称每集最多3个HTTP请求。

Apple普通多候选且支持Range时接资源加载器；明确不支持Range时保留原生首URL直连，该路径不声称可无缝切CDN。单URL冷播保持原有路径。密文C接口仍为generic IO失败，未改C ABI或解码器；native DNS/IP竞速和全部retry策略组合仍未完整还原。

## 清晰度选择与切换

`PlaybackQualitySelector`移植已取证Java默认档位、明确画像目标码率floor，以及SpeedShift的floor分支。默认回退按原Resolution.ordinal，不能用分辨率数字距离替代；画像target不足时保留默认档，而SpeedShift预算不足会选择最低档，二者相同码率的先后规则也不同。多项式/带宽表只接受调用者显式配置，不补0.9×速度等猜测规则。缺失/无效码率按宿主未知值处理。

播放宿主仍默认720p；没有真实目标预测器时不会开启自动选档。可注入`targetBitrateProvider`用于首播/预加载目标码率映射，手动选清晰度后锁档；`useAutomaticQuality`仅供宿主明确恢复该策略，不新增页面或按钮。**当前应用没有注入原生预测器，连续ABR未启用。**普通独立MP4 URL没有原模型的BASH/DASH分段上下文，不能假装实现无缝自动切码率。

手动切换复用有效且不可变的视频模型；选择整条Info，保持URL、备用地址、编码、密钥和有效期一致，不把不同档位合并。选择缓存与源世代隔离，旧返回不能污染新档位；未知/临近过期模型仍重新解析。只清理旧准备与元数据选择，不删除用户离线视频/原始媒体字节缓存。本地固定画质文件不能仅通过修改标签变成另一画质。

`QualitySwitchCoordinator`按首次请求捕获位置，连点只更换目标，取最新真实首帧才结束。原生create可在prepare之前指定initialPositionMs，Apple初始seek完成前不发布0秒首帧。切换保持暂停/播放意图、倍速；用户中途暂停、路由覆盖、后台或离页不会被旧回调强制播放。没有加入原代码未证实的失败自动回滚。

参考执行：从REA方法原文抽取Java并用数据stub运行，19个适用于宿主非空rendition合同的固定向量与Dart结果一致；两个null/empty-model案例不适用于宿主返回一个实际可播条目的接口。原生ABR `_select/_getPredict`及speed predictor未取得算法；原测试APK缺abrmodule原件，native provider深分析也失败，不能宣称完整复刻连续ABR或native速度预测。
